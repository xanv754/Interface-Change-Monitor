## Funcionamiento general de la capa

`presentation/` es una SPA en Next.js (App Router, todo bajo `"use client"` salvo `layout.tsx`) que consume la API de `business/` vía HTTP. La organización sigue un patrón en 3 capas propio, paralelo al patrón `access/`↔`data/` del backend:

1. **`app/`** (UI): páginas y componentes React. Cada página sigue el mismo esqueleto: un estado `modal` que arranca en `{ showModal: true, title: "Cargando...", ... }`, uno o más `useEffect(() => {...}, [])` que llaman a un `Controller` al montar, y al terminar la carga hacen `setModal({...modalDefault, showModal: false})`. La navegación entre secciones (navbar, links "Perfil", "Configuración", etc.) se hace con `<a href=...>` planas, no con `next/link` ni `router.push` (ver Refactor urgente #5).
2. **`controllers/`**: una clase estática por dominio (`SessionController`, `UserController`, `InterfaceController`, `AssignmentController`, `HistoryController`, `StatisticsController`). Es la única capa que aplica alguna regla de negocio del lado del cliente (p. ej. `UserController.getAvailaibleAssignUsers` cruza `ConfigurationSchema.can_receive_assignment` con el rol de cada usuario; `AssignmentController.newAssignments` inyecta `assign_by` desde la sesión activa). El resto de los métodos son *pass-through* casi directos a `models/`.
3. **`models/`**: una clase estática por dominio con el mismo nombre de dominio (`SessionModel`, `UserModel`, etc.), cada una con `private static url = process.env.NEXT_PUBLIC_API_URL ?? ""` y métodos que hacen `fetch` nativo contra un endpoint de `business/api`. Patrón uniforme en los ~20 métodos: `try { ... if (response.ok) return ...; else throw new Error(status+statusText) } catch (error) { console.error(error); return <valor vacío del tipo de retorno> }` — nunca propagan el error hacia arriba, así que un componente no puede distinguir "sin resultados" de "error de red/servidor" (ver Refactor urgente #2).
4. **Sesión/autenticación**: `models/session.ts::TokenCookie` es el único punto que toca el token. Usa `js-cookie` para guardar el JWT en una cookie **no-httpOnly** llamada `token` (con `secure` dinámico según `window.location.protocol` y `expires` sincronizado con el `exp` del propio JWT). El backend además emite, de forma aditiva, una cookie `token` httpOnly equivalente (ver Seguridad #1) que este cliente todavía no consume. Cada modelo que necesita autenticarse llama a `SessionModel.getToken()` (salvo `SessionModel` mismo, que usa `TokenCookie.getToken()` directamente) y arma el header `Authorization: Bearer <token>` a mano en cada `fetch`; no hay un cliente HTTP centralizado (ni interceptor, ni wrapper) — el patrón `if (token) { fetch(...) } else throw new Error("Token not found")` está copiado literalmente en los ~20 métodos de `models/`.
5. **Autorización en la UI**: `presentation/middleware.ts` redirige a `/` cuando no hay cookie `token` en una ruta protegida (chequeo de presencia únicamente, no de validez/rol). Aparte de eso, cada página decide individualmente qué hacer si `SessionController.getInfo()` devuelve `null` (todas hacen `SessionController.logout()`, pero ninguna redirige a `/` tras eso — ver duda de diseño en Comentarios extras). La lógica de "quién ve qué" dentro de una página ya cargada sigue dispersa en cada página/`NavbarComponent`, comparando campos booleanos de `SessionSchema` (`can_assign`, `can_receive_assignment`, `view_information_global`) o `role` contra `RoleTypes`.
6. **Modelo de datos vs. backend**: `schemas/` son `z.object(...)` de Zod (con `type X = z.infer<typeof x>` derivado de cada uno) — cada método de `models/` valida la respuesta real del backend con `.safeParse(...)` antes de devolverla; si el shape diverge, cae al mismo valor vacío que ya usa el resto del archivo para errores de red, en vez de dejar `undefined` silencioso en el JSX.
7. **Exportación a Excel** (`utils/export.ts`, vía `exceljs`) y **filtro de búsqueda en memoria** (`utils/operation.ts::OperationData.filterChangeInterfaces`, un `.some()` sobre `Object.values` convertidos a string) son las únicas piezas de lógica de negocio no ligadas a un fetch.

## Refactorizaciones Urgentes

1. **Duplicación masiva entre páginas casi idénticas.** `app/dashboard/admin/page.tsx` y `app/dashboard/personal/page.tsx` comparten ~80 % de su estructura (tarjetas de estadísticas, buscador, formulario, `InterfaceListComponent`, patrón de modal) con solo el origen de datos y el endpoint de destino distintos. Lo mismo entre `app/history/admin/page.tsx` y `app/history/personal/page.tsx`, y entre `app/components/list/interfaces.tsx` y `app/components/list/history.tsx` (~400 líneas cada uno, prácticamente el mismo JSX de comparación campo-por-campo old/new, repetido una tercera vez en `utils/export.ts` con las mismas 16 columnas ifName/ifDescr/ifAlias/ifHighSpeed/ifOperStatus/ifAdminStatus). Cualquier cambio de campo (agregar un `ifType`, por ejemplo) obliga a tocar 3-4 archivos de forma sincronizada. Se recomienda extraer: (a) un hook `useAsyncResource`/`usePageSession` para el patrón `modal de carga + fetch de sesión + logout en null`; (b) un subcomponente `InterfaceChangeFields` que reciba el objeto y renderice el bloque comparativo old/new, reutilizado por ambas listas; (c) una tabla de columnas compartida entre las dos funciones de `ExportHandler`.
2. **`models/*.ts` — los ~20 métodos idénticos en su manejo de error ocultan la diferencia entre "vacío" y "error".** Todo `catch` hace `console.error` y devuelve `[]`/`false`/`null`/objeto vacío, sin ningún código o mensaje que el `controller`/la UI pueda inspeccionar. No hay forma de que una página distinga "el usuario no tiene historial" de "el backend devolvió 500" o "no hay red" — en ambos casos se ve una lista vacía sin ningún aviso. Se recomienda un wrapper HTTP centralizado (reemplazando el `fetch` manual repetido en cada método) que devuelva un resultado tipado (`{ ok: true, data } | { ok: false, status, error }`) para que la UI pueda mostrar un mensaje de error real en vez de una lista vacía silenciosa.
3. **Sin cliente HTTP centralizado — el bloque `Authorization: Bearer <token>` + `if (token) {...} else throw ...` está copiado en los ~20 métodos de `models/`.** Cualquier cambio (p. ej. manejar un 401 refrescando el token, o agregar un header nuevo) exige tocar todos los archivos de `models/`. Se recomienda un `ApiClient` (o un `fetch` wrapper) único usado por las 6 clases `*Model`.
4. **Sin manejo de expiración/401 de sesión.** Ningún `model` revisa `response.status === 401` de forma especial: un token JWT expirado (dura 9h según REFACTOR-BUSINESS.md) simplemente hace que `response.ok` sea `false`, y el `catch` de cada método devuelve el valor vacío de siempre — la página muestra "sin datos" en vez de forzar un logout/redirect a `/`. El usuario descubre que su sesión expiró solo si intenta un `submit` cuyo modal de error es más explícito, o nunca.
5. **Navegación con `<a href>` planas en vez de `next/link`/`router.push` en `NavbarComponent` y en los enlaces de "Perfil"/dropdowns.** Cada click de navegación fuerza un full page reload (se pierde el estado de React, se re-descarga el JS bundle) en una app que en el resto de los flujos (redirect tras login, tras logout) sí usa `useRouter().push`. Es inconsistente y anula buena parte del beneficio de una SPA de Next.js.

## Análisis de Seguridad

1. **Token de sesión — migración del cliente a la cookie httpOnly, pendiente.** El backend (`icm/business/api/app.py::login`) ya emite una cookie `token` **httpOnly** (`secure`, `samesite=strict`, `max_age` sincronizado con `SecurityController.access_token_expire_minutes`) además del bearer token en el body JSON, y `icm/business/controllers/security.py::CookieOrHeaderOAuth2` ya acepta esa cookie como fallback en cualquier ruta protegida cuando no llega el header `Authorization` — verificado con la suite de `tests/business/` (123 pruebas) y una prueba manual end-to-end (login vía cookie sola autentica contra `/user/info`; el header sigue funcionando igual que antes). Pero `presentation/` **todavía no usa nada de esto**: `models/session.ts::TokenCookie` sigue guardando el token en una cookie no-httpOnly vía `js-cookie` y todo `fetch` sigue mandando `Authorization: Bearer <token>` a mano. Migrar el cliente (dejar de leer/escribir el token en JS, agregar `credentials: "include"` a los fetches) es lo único que realmente cierra el hueco de XSS — queda pendiente, a propósito, para cuando se centralice el `ApiClient` (Refactorización Urgente #2/#3), ya que ese es el único punto donde tocar los ~20 métodos de `models/` no implica duplicar el cambio veinte veces.

2. **Sin `Content-Security-Policy`.** `next.config.ts` ya trae `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy` y `Permissions-Policy`, pero deliberadamente sin CSP (requiere más pruebas por el riesgo de romper la hidratación de Next.js con nonces). Sigue pendiente si se quiere cerrar del todo la superficie de XSS que motiva el punto 1.

## Análisis de Pruebas Unitarias

**PRUEBAS POR IMPLEMENTAR.** No existe ningún framework de testing configurado en `package.json` (sin `jest`, `vitest`, `@testing-library/*`, `playwright`, ni ninguna variante) y no hay un solo archivo `*.test.ts(x)`/`*.spec.ts(x)` en toda la capa. `utils/operation.ts::OperationData.filterChangeInterfaces` y `utils/date.ts::DateHandler` son las piezas más triviales de testear primero (funciones puras, sin DOM ni fetch); `utils/export.ts::ExportHandler` necesitaría mockear `exceljs`/`Blob`/`window.URL`. El resto de la capa (`controllers/`, `models/`) requeriría mockear `fetch` y `js-cookie` — buen candidato para Vitest + Testing Library dado que ya usan Next.js 15/React 19 (mejor soporte que Jest para App Router y Server/Client Components mixtos), pero es una decisión a tomar con el usuario antes de empezar.

## Comentarios extras

- **Duda de diseño abierta — ¿el `logout()` sin sesión válida debería redirigir?** En todas las páginas, el patrón `SessionController.getInfo().then(response => { if (response) setUser(response); else SessionController.logout(); })` limpia la cookie pero **no** hace `router.push(PATHS.LOGIN)` tras el `logout()`. El usuario se queda en la página actual sin sesión (viendo un `NavbarComponent` con `user=null`, que igual renderiza enlaces) — el `middleware.ts` no lo saca de una página ya cargada, solo bloquea la entrada a una nueva sin cookie. No está claro si es un descuido o si se espera que el próximo click en cualquier link autenticado falle "con gracia" — vale la pena decidirlo explícitamente.
- **Resuelto — `/history/assignments` sí filtra por el usuario autenticado.** Verificado end-to-end contra el backend real (login como `admin`, asignación creada a nombre de `user_a`, consulta de `/history/assignments` autenticado como `admin` devuelve `[]`, la misma consulta autenticado como `user_a` devuelve la asignación): el endpoint filtra por el usuario del JWT, no por lo que mande el cliente. `app/dashboard/personal/page.tsx::HistoryController.getHistoryPending()` sí devuelve solo lo del usuario logueado, como se esperaba.
- **Pendiente de verificar:** si cada endpoint de `business/api` valida el rol del usuario del lado del servidor de forma consistente para las rutas de administración (el `middleware.ts` solo chequea presencia de cookie, no rol — la autorización real sigue dependiendo de esto). No verificado en esta sesión.
- **`app/lobby/page.tsx` es un stub sin implementar** (`<main><h1>Lobby</h1></main>`, sin `NavbarComponent`, sin contenido, sin lógica) a pesar de que `NavbarComponent` y el flujo de login/redirect ya asumen su existencia (`PATHS.LOBBY`). Probablemente es trabajo pendiente reconocido, no un defecto — pero conviene decidir su alcance antes o durante la sub-sesión de esta capa.
- **Orden recomendado para lo que queda pendiente:** (1) el `ApiClient` centralizado (Refactor urgente #2 y #3) — es también el momento natural para migrar el cliente a la cookie httpOnly que ya emite el backend (Seguridad #1) y para decidir el redirect tras `logout()`, ya que todo eso toca los mismos ~20 métodos de `models/`; (2) recién ahí la deduplicación grande (dashboard admin/personal, history admin/personal, las dos listas de interfaces, `ExportHandler`, Refactor urgente #1) porque conviene hacerla una vez que el manejo de datos/errores ya sea uniforme, para no duplicar el nuevo patrón en dos lugares y tener que volver a fusionarlo.
- **Pila de testing sin decidir.** Ver "Análisis de Pruebas Unitarias" — Vitest + Testing Library es la recomendación por compatibilidad con Next 15/React 19, pero es una decisión a confirmar con el usuario, no tomada unilateralmente aquí (mismo criterio que se siguió en `access/`/`data/` para decisiones que exceden el archivo en cuestión).
